# 07 用户认证体系

> 基于 Supabase Auth 的项目级认证集成 — 覆盖 Email / OAuth / 匿名五种登录方式与完整 Token 生命周期管理

---

## 1. 用户认证是什么

本项目不自行实现密码哈希或 OAuth 握手，而是直接集成 **Supabase Auth**（`@supabase/supabase-js` SDK），在其基础上构建项目级的用户体系。Supabase Auth 底层提供：

- **多通道登录**：Email + Google + Facebook + Apple + 匿名，统一 `signIn` 入口
- **自动签发 JWT**：登录即得 access_token / refresh_token，无需手动签发
- **OAuth 回调托管**：Supabase 自动处理三方平台的 code→token 交换
- **auth.users 表**：Supabase 内建用户表，与 public.profiles 通过触发器自动同步

本项目在此之上补充了完整的应用层能力：

- **匿名→登录无缝衔接**：游客先用 device_id 浏览，触发支付时弹出登录，历史数据自动迁移到 user_id
- **Cookie + Bearer 双模式**：H5 页面走 Cookie（浏览器自动携带），API 调用支持 Bearer header
- **服务端中间件链**：三阶段身份解析（Bearer → Cookie → 匿名），统一定义权限策略
- **前端组件与 Composable**：封装 `useAuth()` 提供声明式登录状态，H5LoginModal 支持 5 种登录方式一键切换
- **管理后台登录**：管理员通过 profiles.role = 'admin' 标识，Admin 中间件自动拦截校验

> 本模块是 [04-Supabase数据库集成.md](./04-Supabase数据库集成.md) 中「Supabase Auth」的工程化补充，聚焦于项目内的集成架构、前后端协作和完整认证闭环。

## 2. 前置准备

### 2.1 已完成 Supabase 项目初始化

确保 Supabase 云项目已创建，环境变量已配置。参考 [04-Supabase数据库集成.md](./04-Supabase数据库集成.md) 第 2-4 节。

```bash
# 验证 Supabase 连接
npm run test:supabase
```

### 2.2 配置 OAuth Provider（如需社交登录）

如需 Google / Facebook / Apple 登录，需在 Supabase Dashboard 和各三方平台完成配置：

| Provider | Supabase Dashboard 入口 | 所需信息 | 难度 |
|----------|--------------------------|----------|------|
| Google | Authentication → Providers → Google | Client ID + Client Secret | ⭐ 低 |
| Facebook | Authentication → Providers → Facebook | App ID + App Secret | ⭐⭐ 中 |
| Apple | Authentication → Providers → Apple | Service ID + Key ID + Private Key | ⭐⭐⭐ 高 |

> 开发阶段建议先只配置 Google（申请最快，`console.cloud.google.com` → API & Services → Credentials），Facebook 和 Apple 在对接支付/上线前补齐即可。

### 2.3 确认 Cookie 域名

H5 登录依赖 Cookie 传递 token，本地开发时注意：

```env
# 本地开发使用 localhost，无需额外配置
# 生产环境需确保域名与 Supabase Redirect URL 配置一致
SITE_URL=http://localhost:3000
```

## 3. 支持的登录方式

| 登录方式 | Provider | 实现机制 | 适用场景 |
|----------|----------|----------|----------|
| Email + Password | `email` | Supabase `signUp` / `signInWithPassword` | 通用注册登录 |
| Google | `google` | Supabase `signInWithOAuth` | 海外主流用户 |
| Facebook | `facebook` | Supabase `signInWithOAuth` | 东南亚/拉美用户 |
| Apple | `apple` | Supabase `signInWithOAuth` | iOS 用户（App Store 审核要求） |
| Anonymous | `anonymous` | Supabase `signInAnonymously` + device_id | 先浏览后登录 |

## 4. 认证流程全览

```
H5 用户打开页面
    ↓ (匿名浏览)
匿名用户 cookie (device_id)
    ↓ (点击预约/支付)
弹出登录引导 Modal
    ├── Email 注册/登录 ──→ Supabase signUp / signInWithPassword
    ├── Google 登录 ──────→ Supabase OAuth (provider: google)
    ├── Facebook 登录 ────→ Supabase OAuth (provider: facebook)
    └── Apple 登录 ───────→ Supabase OAuth (provider: apple)
    ↓
access_token 写入 Cookie → server middleware 自动识别
    ↓
profiles 表自动创建 → orders 表 user_id 衔接
```

### 核心设计原则

- **客户端直连 Supabase Auth**：使用 `@supabase/supabase-js` SDK，不在服务端重复实现 OAuth 流程
- **Cookie + Bearer 双模式**：H5 走 Cookie，App 走 Bearer，server middleware 已支持两者
- **匿名→绑定无缝衔接**：匿名用户行为数据存 device_id，绑定后自动迁移到 user_id

## 5. 数据库设计

### 5.1 profiles 表字段（0001_core.sql）

| 字段 | 类型 | 说明 |
|------|------|------|
| `email` | TEXT | 用户邮箱（从 auth.users 同步） |
| `username` | TEXT | 用户名（最长 50 字符） |
| `avatar_url` | TEXT | 用户头像 URL |
| `display_name` | TEXT | 显示昵称 |
| `auth_provider` | TEXT | 登录来源：email / google / facebook / apple / anonymous |
| `provider_id` | TEXT | 三方平台原始 ID |
| `device_id` | TEXT | 设备指纹（匿名用户标识） |
| `is_anonymous` | BOOLEAN | 是否匿名用户 |
| `email_verified` | BOOLEAN | 邮箱是否已验证 |
| `phone` | TEXT | 手机号码 |

### 5.2 自动 Profile 创建触发器

`handle_new_user()` 函数在 `auth.users` INSERT 时自动触发，从 `raw_user_meta_data` 提取信息写入 profiles。OAuth 用户自动设置 `email_verified = TRUE`。

### 5.3 认证日志

登录日志合并到统一活动日志表 `activity_logs`，认证类记录使用 `category = 'auth'`。

## 6. 服务端 API

| 路由 | 方法 | 功能 |
|------|------|------|
| `/api/v1/auth/register` | POST | 邮箱注册 + 自动创建 profile |
| `/api/v1/auth/login` | POST | 统一登录入口（邮箱 / OAuth / 匿名） |
| `/api/v1/auth/callback` | GET | OAuth 回调（code → token 交换） |
| `/api/v1/auth/me` | GET | 获取当前用户 profile |
| `/api/v1/auth/profile` | PATCH | 更新用户信息（昵称 / 头像 / 手机） |
| `/api/v1/auth/link` | POST | 匿名用户绑定邮箱 |
| `/api/v1/auth/logout` | POST | 登出 + 清理 Cookie |

### login.post.ts 三种模式

```ts
POST /api/v1/auth/login  { email, password }           // 模式 1: 邮箱密码
POST /api/v1/auth/login  { provider: 'google', ... }    // 模式 2: OAuth 跳转
POST /api/v1/auth/login  { anonymous: true, device_id } // 模式 3: 匿名登录
```

## 8. Token 生命周期管理

| Token 类型 | 有效期 | 存储位置 | 说明 |
|------------|--------|----------|------|
| Access Token | 1h | `sb-access-token` Cookie | 短期 JWT，server middleware 验证 |
| Refresh Token | 30d | `sb-refresh-token` Cookie | 自动续期 access_token |
| Device ID | 365d | `device-id` Cookie | 设备指纹，匿名用户标识 |

### Cookie 同步机制

`app/plugins/supabase-auth.client.ts` 监听 `onAuthStateChange`：
- `SIGNED_IN` / `TOKEN_REFRESHED` → 写入 Cookie（`SameSite=Strict; Secure` for HTTPS）
- `SIGNED_OUT` → 删除 Cookie

## 9. Server Middleware 身份解析

`02.auth.ts` 中间件 Token 来源优先级：

1. **Bearer header**（`Authorization: Bearer xxx`）
2. **Cookie**（`sb-access-token`）
3. **匿名降级**（`device-id` Cookie → role: `anonymous`）

## 10. 权限守卫

`04.auth-guard.ts` 中间件对以下路由强制要求登录：

| 路由前缀 | 要求 |
|----------|------|
| `/api/v1/payments/*` | 必须已登录（非匿名） |
| `/api/v1/orders/*` | 必须已登录 |
| `/api/v1/auth/profile` | 必须已登录 |
| `/api/v1/auth/me` | 必须已登录 |
| `/api/v1/campaigns/*` | 公开 |

### 站点访问密码（可选）

`05.access-guard.ts` 中间件在所有鉴权之后执行。当配置 `SITE_ACCESS_PASSWORD` 时，对所有页面和 API 文档路径进行密码保护。认证相关 API 和 Stripe Webhook 回调始终放行。

## 11. 匿名 → 绑定数据迁移策略

```
1. 匿名用户浏览 → 行为数据关联 device_id
2. 触发绑定 → POST /api/v1/auth/link 绑定邮箱
3. 身份转换 → profiles.is_anonymous = false
4. 数据归属 → 新数据关联 user_id，历史数据可通过 device_id 回溯
```

## 15. 常见问题

### Q: 邮箱注册后用户无法登录

检查 Supabase Dashboard → Settings → Email Auth → **Confirm email** 是否开启。测试阶段可关闭。

### Q: OAuth 回调报错 `Invalid redirect URL`

在 Supabase Dashboard → Authentication → URL Configuration → **Redirect URLs** 中添加当前域名。

### Q: Token 过期后请求返回 401

正常情况下插件会在 token 过期前自动续期。如仍 401，检查 `sb-refresh-token` Cookie 是否存在。
